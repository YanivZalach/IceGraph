The Graph view shows all Iceberg metadata objects in your selected range as a directed acyclic graph. Each node is a file, except the Catalog node and deletion vectors, which get one node each even when several share a Puffin file. Links connect node edges, with arrowheads pointing from parent to child.

### Node types

- **Metadata file** - JSON file describing the full state of the table at one point in time: schema, partition spec, properties, and the snapshots it knows of. It links only to the snapshots it points to: its current snapshot and the head of each branch. The other snapshots it lists, kept for time travel until they expire, are not linked; they appear in `pointed_snapshots_files` in its details panel. The statistics files it lists appear in `pointed_table_statistics_files` and `pointed_partition_statistics_files`. Its `format_version` is the Iceberg format version the table had when the file was written

- **Snapshot** - Avro file that represents a point-in-time version of the table produced by a data operation (append, overwrite, etc.). On format version 3 tables it shows `first_row_id`, the row ID where the commit's row IDs start, and `added_rows`, the most row IDs it could have assigned

- **Manifest** - tracks which data files exist and stores per-file statistics. On format version 3 tables, a data manifest shows its `first_row_id`, the row ID its data files count up from. When branches give the manifest different values, `first_row_id` is hidden and `first_row_id_by_snapshot` lists each value with the earliest snapshot that gave it

- **Data file** - the actual Parquet, ORC, or Avro file containing your rows. IceGraph is not reading the data file: all of the data shown comes from the manifest entries that point at it. When available, the details panel also shows human-readable per-column metrics derived from the manifest entry, including the inferred metadata size that is not represented by reported column sizes. On format version 3 tables, files written by an update or merge can also show metrics for the row lineage columns `_row_id` and `_last_updated_sequence_number`; modified rows store null for `_last_updated_sequence_number`, and when those rows are read Iceberg substitutes the data sequence number of the file's manifest entry. For `geometry` and `geography` columns, the lower and upper bounds are the corners of a bounding box around every value in the file, shown with their `x`, `y`, and, when present, `z` and `m` coordinates. For `variant` columns, each bound lists the lower or upper value of each field inside the variant, keyed by the field's JSON path, such as `$['user']['age']`. Iceberg writes variant bounds only for shredded variant columns, so most variant columns show none. On format version 3 tables, a data file shows its `first_row_id`: its rows have row IDs from `first_row_id` to `first_row_id` + `row_count` - 1. Iceberg leaves newly added files without a stored value and assigns one when it reads the manifest; IceGraph assigns the same value. After an upgrade to version 3, branches can give the same file different row IDs. When they do, `first_row_id` is hidden and `first_row_id_by_snapshot` lists each value with the earliest snapshot that gave it. Delete files, and files written before a table was upgraded to version 3 that no version 3 snapshot in the selected range lists, have no row IDs, so the field is hidden

- **Deletion vector** - a format version 3 delete: a bitmap of deleted row positions for one data file, stored in a Puffin file. One Puffin file can hold deletion vectors for many data files, so each deletion vector is its own node, with its own partition, row count, and status in each manifest. Its node ID is the Puffin file path followed by `#` and its `content_offset`. `referenced_data_file` is the data file it deletes from, `row_count` is the number of deleted rows, `content_size_in_bytes` is the size of the vector, and `file_size_in_bytes` is the size of the whole Puffin file

- **Table statistics** - Puffin file with column statistics, such as distinct value counts, for one snapshot. Drawn in amber left of the metadata files and linked from the metadata file that added it. IceGraph shows what the metadata file says about it, without opening it

- **Partition statistics** - Parquet file with per-partition counts, such as records, files, and deletes, for one snapshot. Drawn in silver left of the metadata files and linked from the metadata file that added it. IceGraph opens it and shows how the data is spread across partitions, plus a sample of the most recently updated partitions. The distribution caption **Per partition across all partitions** means it covers every partition in the statistics file. The details show `partitions_with_deletes` as a separate count, counting a partition when it has position delete files, equality delete files, or deletion vectors, and treating missing or null counts as zero. Samples use a shared set of fields across the collected statistics files. Only the newest files, up to a configured limit, are opened; older files show only their metadata fields and a warning

- **Catalog** - not a file. It is the entry point to the table: the catalog is what points to the current main metadata file, and every read of the table starts there. It is drawn larger and highlighted, labelled with the table name, and sits at the top of the metadata column, with a downward arrow to the main metadata file. Its details show the table properties that do not change between updates: name, UUID, location and format version

- **Unreadable file** - a file whose metadata could not be obtained is drawn in red and shows the reason in its details panel. The rest of the graph still loads

### Interactions

- Click a node to select it and open its details in the side panel

- Drag a node to reposition it
- Scroll to zoom, drag the background to pan

### Details panel

The panel on the right lists every metadata field for the selected node. The header shows the file type, path, and timestamp; fields below use the same layout as Timeline and other views.

- **Virtual read** - data files, position and equality delete files, and table statistics files show this badge at the top of the panel when the backend marks them as virtually read. Hover, focus, or click the label for its explanation: details come from Iceberg metadata. IceGraph does not read this file or verify that it exists.

- **Resize** - drag the grip handle on the left edge of the panel to widen it. Wider panels give text fields more room and show more lines before you need to expand a field.

- **Fullscreen** - click the expand button in the panel header to fill the graph area. Click the compress button or press **Esc** to exit.

- **Copy** - click the clipboard icon inside any field to copy its value.

- **Long values** - fields with many lines can be expanded or collapsed individually with **▼** / **▲**.

### Reading the graph

Nodes shared across multiple snapshots mean Iceberg reused those files, data that didn't change is never rewritten. Seeing many shared data files between snapshots is normal and efficient. A snapshot with no shared manifests or data files means a full overwrite occurred.
